## 字段约定

- **需求ID**：kebab-case，如 `otp-login`，同时作为 Spec 目录名。
- **来源**：提出人 / 渠道 / 工单号，便于追溯。
- **优先级**：P0（阻塞）/ P1（重要）/ P2（一般）。
- **用例文档**：`.agentbuddy/specs/<需求ID>/usecases.md` 的相对路径。
- **特性文档**：`.agentbuddy/specs/<需求ID>/requirements.md`，即 Spec 的 requirements 阶段产物。
- **Spec 目录**：存在即表示已进入 Spec 流程；看板按此目录扫描。

## 流转规则

1. 新需求由 `req-to-usecase` 登记为「待分析」，分配需求ID。
2. Skill 分析后产出 `usecases.md`，状态改为「用例已生成」，等待确认。
3. 用户确认用例与特性文档后，状态改为「规格已确认」，进入现有 `spec-advance` 流程（design → tasks）。
4. tasks 确认后状态「开发中」，Spec `stage: done` 时改为「已完成」。
5. 状态变更须同步更新本表与对应 Spec 的 `STATUS.md`。


## 需求详情

> 以下为 2026-11-24 使用者走查时登记的原始说明，供 Loop 做 `req-to-usecase` 时使用。每条只处理一个可独立交付的问题。走查用的是源码前端 `http://localhost:19527`（Flask `127.0.0.1:5051`），当前分支 `feat/acp-experience-stats`；不要改 llm.yaml / MCP / Skills / Codex auth.json，不要把 Spec 看板重新挂回顶栏，不要在未确认前改业务代码。

### header-sync-nav-layout

- **现象**：在「LLM 配置」「Skills 管理」「记忆」等会显示同步栏的页面，顶栏同一行同时放了 8 个一级导航、版本胶囊、同步控件（N 个目标 / 点击同步 / 自动 / 清除设置）、官网、主题、登录/注册。1440 宽时，「Token 市场」按钮与「0 个目标」命中区域重叠约 14px（Token 右边缘 839.8，目标左边缘 826.2）。点目标选择器左侧会进 Token 市场，而不是打开 IDE 勾选浮层。版本胶囊也被挤成只剩 `vdev`，升级提示看不清。同步栏浮层里的「清空」是清空勾选，顶栏「清除设置」是删除已写入 AIDE 的 LLM 配置，两个词挨得很近，容易点错。
- **在哪看到**：打开 `?tab=env`（LLM 配置）看顶栏；Playwright `elementFromPoint` / 点击「0 个目标」时被 `Token 市场` 拦截。Skills、记忆等带同步栏的页同样拥挤。
- **为什么不合理**：同步到哪些 IDE、是否立即同步，是 LLM 页的核心操作，却被塞进全局导航里且会被导航项挡住。源码注释本来就把 SyncBar 写成「Header 下方 44px 工具栏」，实际却放在 header actions 里。用户完不成「先勾选 IDE 再同步」。
- **建议**：
  1. 把同步栏移到顶栏下方一条独立工具条（或页内操作区），导航只负责切页，保证「N 个目标」整块可点。
  2. 收敛一级导航：将「插件管理 / 插件市场 / 插件构建 / Token 市场」收进「插件」分组；密钥可进设置或该分组。不要把 Spec 看板挂回顶栏。
  3. 空间不足时版本胶囊不要截断到看不出「有新版本」。
  4. 浮层「清空」改成「取消全选」之类，与破坏性「清除已同步的 LLM」明确区分。
  5. 可选：默认落地页从插件市场改为 AIDE 管理或 LLM 配置，更符合「配好再同步」的主路径。

### server-settings-before-login

- **现象**：未登录时顶栏只有「登录 / 注册」，没有服务器设置入口。「服务器设置」只出现在已登录头像菜单里。登录/注册弹窗只有用户名和密码，不显示当前 Server URL，也不能改地址。
- **在哪看到**：未登录打开应用 → 点「登录」。对照 `Header.vue`：`openServerDialog` 仅挂在已登录的 `user-menu-item`。
- **为什么不合理**：登录和插件市场都要打远程服务器。默认地址不对、或用户想改到 `http://linkagent.icu:5001` 时，必须先登录，但登录又依赖这个地址，形成死结。市场连不上时也没法从登录流程里修正。
- **建议**：未登录也在顶栏放齿轮/「服务器」入口；登录弹窗展示当前地址并提供「修改服务器」链接。不要在检查或测试连接时自动保存并覆盖用户已保存的地址，除非用户点了保存。

### acp-empty-spec-sidebar-layout

- **现象**：ACP 体验页是三栏：左侧 Agent 列表、中间黄底统计卡 + 大块黑色对话区、右侧常驻「Spec 进度」。未选择 Agent 时，模型/Skills/MCP 都是「—」，对话区只剩一句说明，右侧只有「安装并使用 spec-workflow 插件后，最近 Spec 进度会显示在这里」。页头还有「刷新中…」，和 Spec 侧栏的「刷新」并排，空列表时也像一直在刷新。
- **在哪看到**：顶栏「ACP 体验」（`?tab=acp`），本地当时是「共 0 个 · 可用 0 个」。
- **为什么不合理**：空态被三栏空白占满，真正要做的事（去选/启动一个 ACP Agent）不够突出。Spec 侧栏在没有 Spec 时仍占一整列，挤压对话区。不要把 Spec 看板重新挂到顶栏。
- **建议**：无 Spec 时把右侧收成按钮或抽屉，有进度再展开。空态改成单一引导（例如「去 AIDE 管理启动 ACP」）。模型/Skills/MCP 统计在未选 Agent 时不必占三大块卡片。分清「正在刷新」和「刷新」按钮，刷新结束后去掉「刷新中…」。

### marketplace-remote-fail-banner

- **现象**：远程市场请求失败后，页面仍展示 10 条带下载量的插件卡片，只在「全部插件」旁标一个小「示例」。`isMock` 的 title 是「当前为内置示例数据，发布本地插件后将自动替换」，没有说远程连接失败，也没有当前服务器地址或「去设置」入口。筛选栏在右侧拉出一长串几乎都是「1」的标签，进一步占宽。
- **在哪看到**：默认落地「插件市场」。走查时 `http://123.60.75.27:5001/api/marketplace` 被 CORS 拦截（此功能分支默认地址尚未跟上 main 的 `http://linkagent.icu:5001`），页面回落到 `MOCK_ITEMS`。
- **为什么不合理**：看起来像真市场，用户可能去点「安装 / 下载」才发现是示例；也不知道要改服务器。失败原因被藏在小标记里。
- **建议**：远程失败时在列表上方用横幅写清「无法连接市场服务器 {url}，当前是内置示例」，并提供「服务器设置」入口（需与 `server-settings-before-login` 一起才能在未登录时用）。保留「示例」标记。筛选可改成默认收起或顶部标签，不要用一条占满右侧的长清单抢空间。

### aide-catalog-grouping

- **现象**：AIDE 管理把每个产品的 CLI / App / VSCode 插件 / IDEA 插件 / ACP / Remote Web 等形态都平铺成一行行图标墙，未安装的占了大半屏，要很长下拉才能看完。顶部有「全部 AIDE」和少量快捷筛选，但仍是「先看完整目录」。
- **在哪看到**：顶栏「AIDE 管理」。
- **为什么不合理**：使用者通常只关心本机已安装、或某几个产品。平铺目录让「我的环境」和「还能装什么」混在一起，扫描成本高。
- **建议**：按产品分组，安装形态放在组内展开。默认先展示「已安装 / 已检测」，完整目录用筛选或「全部」查看。不要做成又一个顶栏入口。

### memory-duplicate-sync

- **现象**：记忆配置页本身有「导入 / 导出 / 同步到 IDE / 保存」，顶栏同步栏同时出现「将同步记忆到支持的 IDE / 点击同步 / 自动」。两个同步入口含义接近，成功或失败反馈也不在同一处。
- **在哪看到**：Agent 配置 → 记忆（`?tab=memory`）。
- **为什么不合理**：同一件事两个按钮，不知道该用哪一个；若顶栏已改成独立工具条（见 `header-sync-nav-layout`），页内按钮还在就会继续重复。
- **建议**：只留一处同步。若保留顶栏/工具条同步，页内「同步到 IDE」改为指向同一动作或去掉；页内「保存」只负责保存记忆内容。

### register-password-hint-mismatch

- **现象**：注册弹窗密码框 placeholder 写「至少 6 位」，提交逻辑和登录改密都要求至少 8 位。
- **在哪看到**：顶栏「注册」。代码：`AuthDialog.vue` 的 placeholder 为「至少 6 位」，`submit()` 里 `password.value.length < 8` 才报错。
- **为什么不合理**：按提示输入 6–7 位会被拒绝，提示和规则不一致。
- **建议**：placeholder、校验文案和规则统一为至少 8 位（与改密弹窗一致）。


### auth-network-misreport

- **现象**：未登录、默认服务器不可达（本分支默认仍是 `http://123.60.75.27:5001`，预检被 CORS 拦截）时，登录弹窗提交后显示「用户名或密码错误」，像是账号错了。同样网络失败，注册弹窗显示原始英文 `Failed to fetch`。两种提示都不提服务器连不上，也没有改地址的入口。在隔离会话里把地址改成 `http://linkagent.icu:5001` 后，错误密码才收到真正的 401，此时「用户名或密码错误」是对的。
- **在哪一步**：首次/未登录 → 点登录或注册并提交。空表单校验「用户名和密码不能为空」是对的。
- **为什么不顺**：用户会被带到改密码/再试账号，而真正卡住的是服务器地址；和「未登录不能改服务器」叠加后更走不下去。
- **建议**：网络/CORS/5xx 时明确写「无法连接服务器 {url}」，不要复用「用户名或密码错误」；注册不要把 `Failed to fetch` 直接给用户。需要改地址时提供服务器设置入口（与已有 `server-settings-before-login` 衔接）。不要在测试连接时自动覆盖用户已保存的地址。

### marketplace-mock-install-failed-fetch

- **现象**：落地插件市场因远程失败回落到 10 条示例后，「热门推荐」和列表里的「安装」仍可点（下载在部分位置会禁用并提示「示例数据，无法下载」）。点击安装会请求 `/api/marketplace/install?id=mock-react-fullstack`，失败后右上角 toast「安装失败: Failed to fetch」。不说明当前是示例、市场没连上，也没有下一步。
- **在哪一步**：未登录打开应用 → 浏览市场 → 点「安装」或「详情」后安装。
- **为什么不顺**：示例看起来像真插件（有下载量），用户点安装只看到英文 Failed to fetch，不知道要改服务器还是根本装不了示例。这与「失败时悄悄展示示例」（已有 `marketplace-remote-fail-banner`）是同一路径上的下一步动作问题。
- **建议**：示例数据上禁用或明确标注「示例，无法安装」，与下载按钮一致。失败时用中文说明原因（示例 / 无法连接 {url}），并给出服务器设置入口。不要只 toast `Failed to fetch`。

### llm-disabled-default-silent-autosave

- **现象**：打开「LLM 配置」时，默认源是 `bigmodelCoding`，卡片同时标「默认」和「未启用」，默认模型是「请选择…」。页面有 `watch(activeSource/activeModel) → autoSave()`，进入后约 0.5 秒会静默 `POST /api/llm`，被后端 400 拦截：「默认 LLM Provider 已禁用或不存在」。`saveEnv(true)` 失败不 toast。点「点击同步」在 0 个目标时会正确提示「请先选择目标 IDE」；即便勾了 IDE，这个默认状态也会在校验时拦住同步。
- **在哪一步**：配 LLM → 准备勾选 IDE 并同步。未改 llm.yaml，也未真实同步。
- **为什么不顺**：主路径一开始就是「看起来有默认源、其实已禁用」，自动保存失败还看不见。用户会以为配置已好，同步时才失败或一直搞不清要先启用还是改选。
- **建议**：默认源已禁用时，在「默认 LLM 源」处给出可见提示「当前默认源未启用，同步前请启用或改选」，不要在进页时对非法默认做静默保存；若自动保存失败必须明确报出来。不要为修展示而改写用户的 llm.yaml，除非用户自己点了启用/改选。

### aide-chat-test-wrong-agent

### config-pages-sync-path-inconsistent

### acp-availability-ignores-detected-path

### acp-connect-progress-feedback

- **现象**：在 ACP 体验页选中可连的 Cursor 并点「连接」，约 40 秒才出现 session 就绪。期间按钮和状态主要是「连接中…」「系统正在连接 Cursor…」。日志中有「authenticate(cursor_login) 未完成（将继续尝试 session/new）：等待 authenticate 响应超时（>8.0s）」，随后仍继续并显示已连接。发出测试 prompt「请只回复：pong」后，发送按钮变成「等待…」，12 秒内没有 Agent 回复（随后点「清空」结束会话，避免留下进程）。统计区在前几秒也一直「读取中」，页头曾长时间显示「刷新中…」。
- **在哪一步**：ACP 体验 → 选 Agent → 连接 → 发一条 prompt。
- **为什么不顺**：等待很长且只有「连接中」，中途的 authenticate 超时像失败又不是失败；发出 prompt 后同样缺少是否还在跑的说明，用户容易提前放弃或重复点击。
- **建议**：连接过程展示阶段（启动进程 / 认证 / 建立会话）和大致耗时；authenticate 超时要用可读的状态说明是否继续。发送后保留「等待回复」直到成功、失败或超时。页头「刷新中…」只表示列表刷新，不要和连接过程混在一起（空态布局问题见已有 `acp-empty-spec-sidebar-layout`）。

### ide-token-usage-stats

- **现象**：使用者希望集成「token 消耗量」功能：能按已支持的 IDE / Agent 统计实际用量，并在界面展示。这与现有「Token 市场」不是同一件事——Token 市场（`desktop/frontend/src/views/TokenView.vue`，顶栏 `?tab=token`）是各厂商 Coding Plan / Token 套餐的发现与购买入口，展示的是套餐价格、额度与计费类型，不是本机或账号里已经消耗了多少 token。
- **在哪看到**：使用者提出「想集成 token 消耗量，统计支持的 IDE 然后显示用量」。仓库现状：未见按 IDE 汇总 token / 请求数 / 费用的界面。密钥页的 `usages`（`stores/keys.ts` / `KeysView.vue`）只表示某个 Key 被 `mcp.yaml` / `llm.yaml` 引用，不是消耗量。ACP 体验页已有统计块（`desktop/acp_stats.py`，接口 `GET /api/acp/stats`），只读扫描飞翼源配置与各 AIDE 落盘的模型 / Skills / MCP **数量**；`desktop/acp_sessions.py` 中未检索到 token / 用量字段，当前不会顺带记录对话消耗。
- **为什么不合理**：配置中心已经能检测并同步多个 IDE，但使用者看不到各目标实际花了多少 token。若把用量塞进 Token 市场，会和套餐购买混在一起。
- **建议**：
  1. 按已支持的 IDE / 同步目标 / ACP Agent 统计并展示用量（能拿到的展示 token、请求数、费用、日期范围等；拿不到的标明「暂无数据源」）。不要和 Token 市场的套餐购买信息混在同一套数据里。
  2. 界面位置（新页，还是挂到已有 AIDE 管理 / ACP 体验 / 头部）由后续 `req-to-usecase` 再定。可参考但不必照搬 `docs/superpowers/specs/2026-08-15-agentbuddy-control-tower-ui-design.md` 中「IDE Token 用量 / 按 Provider、IDE、模型和时间查看消耗」的设想——那是设计稿，当前并未落地。
  3. 分析阶段一并写清更新频率、权限与隐私（只读本地文件 vs 需要用户账号 / API Token；导出不得带出密钥或完整本机路径）。
- **初步核查（供分析用；本条登记时未改业务代码，也未对每个 IDE 的本地日志 / CLI / 账号 API 做完整取数验证）**：
  - 支持的 IDE / 目标以 `cli/lib/ide/ide.yaml` 的 `install_meta` / `detect_meta` 为准（与 AIDE 检测、安装同源）。当前条目包括：CherryStudio、Claude、Codex、Cursor、Trae、TraeCN、TraeSoloCN、OpenCode、DeepSeek、Qoder、QoderCN、OpenClaw、Hermes、OpenWorker、WorkBuddy、ZCode、IDEA、KimiCLI、KimiCode、KimiWork、Pi、CommandCode、VSCode、Copilot、Cline、CodeBuddy（另有隐藏占位 `Agents`）。适配器在 `cli/lib/ide/*.py`。
  - 配置了 `acp_install`、可作为 ACP Agent 的有：Claude（`claude acp`）、Codex（`codex acp`）、Cursor（`cursor agent acp`）、TraeCN（`trae acp`）、OpenCode（`opencode acp`）、KimiCode（`kimi acp`）、Copilot（`npx -y @github/copilot-language-server@latest --acp`）、Cline（`npx -y cline@latest acp`）。
  - 在桌面后端与前端业务代码中检索 `input_tokens` / `output_tokens` / `token_count` / `消耗量` 等，未发现已实现的用量采集。上述设计文档写过「用量记录来自 Provider/IDE API 或本地估算服务」，但没有对应实现。
  - **未核实、不要编造**：各 IDE 是否能从本机日志、统计文件、CLI 子命令或账号 API 取到可信用量，本条登记时没有逐个打开本地数据目录或对照官方文档验证。后续分析必须只根据实际找到的来源下结论，并区分：可无账号本地读取、需要用户 token/API、当前完全拿不到。做不到的 IDE 要在用例里明确写出。


### llm-advanced-config-menu

- **现象**：AgentBuddy 本身已有 LLM 网关功能，但「这个界面没有涉及好」。网关能力挤在现有「LLM 配置」页里，和 Provider 编辑混在一起，不容易发现。使用者提出方案：「LLM 高级配置新开一个菜单」，把网关等高级能力放进这个新菜单，不要一直堆在现有 LLM 页里很难发现。
- **在哪看到**：顶栏导航（`desktop/frontend/src/App.vue` 的 `tabs`）在「Agent 配置」分组下只有一项 `env` → 文案「LLM 配置」，没有「LLM 高级配置」或「网关」菜单；`Header.vue` 也只消费这套 tabs。打开「LLM 配置」后，页面主体是 Providers 列表与协议编辑（`LlmView.vue` 标题「LLM Providers」）；「LLM 网关（多协议路由）」整块在同页靠下：可添加路由、启动/停止网关、折叠「高级网关设置」（listen_host / listen_port / 网关密钥）。默认 LLM 源下拉里可选「LLM 网关」（`GATEWAY_SOURCE`），与 Provider 二选一。产品背景：定位是给 ACP 等工具加翅膀；与竞品 Magpie 有点类似，也有网关能力，但界面没把这块展开好。
- **为什么不合理**：后端与 CLI 侧网关能力已经存在（见初步核查），界面却没有独立入口，高级能力藏在 LLM 配置页底部，和日常改 Provider / api_key 的路径搅在一起，和「给 ACP 装翅膀 / 本机网关」的定位不匹配。
- **建议**：
  1. 顶栏新开「LLM 高级配置」（或等价命名）菜单，把网关路由、启停、监听地址/端口/密钥等高级项迁过去；现有「LLM 配置」保留 Provider / 默认源等日常项，避免继续堆在一页。
  2. 默认源里「LLM 网关」选项与新菜单的关系（跳转、状态摘要、是否仍可在 LLM 页一键选用）由后续 `req-to-usecase` 定，不要在分析前拆散现有互斥校验。
  3. 不要和 Token 市场、密钥页混用；本条只改信息架构与入口，不要求本轮改网关协议本身。
- **初步核查（供分析用；本条登记时未改业务代码）**：
  - 前端：网关 UI 与启停逻辑均在 `desktop/frontend/src/views/LlmView.vue`（约「LLM 网关」区块与 `toggleProxyRun` / `addGatewayRoute`）；`env` store 提供 `generateProxyConfig` / `startProxyServer` / `stopProxyServer`；导航无独立 key。
  - 后端：`desktop/config_server.py` 提供 `GET /api/proxy/start`（SSE 拉起 litellm）、`GET /api/proxy/stop`；从 `llm.yaml` 的 `proxy.gateway` 读 `listen_host` / `listen_port`；配置文件落在 `config/proxy/config.yaml`（模板 `template/proxy/config.template.yaml`）。
  - CLI / 同步：`cli/lib/llm.py` 在 `proxy.gateway.enabled` 时把 IDE 环境变量指到网关，并生成 `PROXY_MODEL_LIST`；`config/llm/llm.yaml` 已有 `proxy.gateway` 段（含 `base_url: http://127.0.0.1:4000/v1`）。
  - **未核实、不要编造**：本条未在运行中的界面上逐一点击验证网关启停是否成功，也未对照 Magpie 做功能对标清单；后续分析只根据实际代码与可复现行为下结论。

### sync-get-triggers-force-all

- **现象**：对运行中的源码服务 http://127.0.0.1:5052 发 GET /api/sync，接口以 SSE 流直接拉起 `python -m agentctl.agentctl sync --ide All --force --scope llm,mcp,skill,plugin`，没有目标确认、没有「将写入哪些 IDE」预览。本次实测流里立刻打出 `[ERROR] 默认 LLM Provider...` 后中断；包装版 `http://127.0.0.1:5050/api/sync` 同源路径则长时间无结束（观察超过 2 分钟仍挂起）。顶栏「点击同步」之外，只是探测 API 也会触发写盘级同步。
- **在哪看到**：办公机 2026-11-24；源码 Flask `5052`（`version: dev`，分支 `feat/acp-experience-stats`）与包装 `AgentBuddy 3.22.3`（`5050`，包体 2026-10-21）。未在 GUI 点「清除设置」；未改产品代码。
- **为什么不合理**：同步会改各 IDE 的 LLM/MCP/Skills/插件配置，却挂在无 body 的 GET 上且默认 `All --force`，和「先勾选目标再同步」的主路径冲突，也容易被健康检查、浏览器预取或误打开链接误触发。失败时只在 SSE 文本里报 LLM 默认源问题，GUI 若未接流就看不到。
- **建议**：
  1. 破坏性同步只允许 `POST`，并要求显式 `ides` / `scope`；`GET /api/sync` 仅返回状态或改为 405。
  2. 即使内部调试保留 GET，也禁止默认 `All --force`；至少与 UI 当前勾选目标一致，并先返回将写入路径清单。
  3. SSE/UI 同步失败（含「默认 LLM Provider 已禁用或不存在」）必须在界面可见，不能只写在事件流里。

### dual-runtime-config-split

- **现象**：同一办公机同时跑包装 `127.0.0.1:5050`（`AgentBuddy.exe` 3.22.3，配置根在 `%LocalAppData%\Programs\AgentBuddy\config`）与源码 `127.0.0.1:5052`（项目 `D:\yxz\projects\agentbuddy\config`）。两边 `/api/skills/installed` 结果完全不同：包装约 156 条且大多 enabled；源码只有 7 条（`req-to-usecase` / `spec-*` 等）且全部 enabled=false。包装 `ui-state.ideSyncTargets` 为 `Pi`、`WorkBuddy`；源码 ui-state 无同一字段。Cursor 里已有 200+ 条指向包装 `.agents\skills` 的 junction，但源码侧「已安装技能」几乎为空，ACP 统计页却显示 Cursor skills count=252。
